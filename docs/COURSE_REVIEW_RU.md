# Разбор курса «Production Agentic RAG» (arXiv Paper Curator)

Документ описывает курс [jamwithai/production-agentic-rag-course](https://github.com/jamwithai/production-agentic-rag-course)
(форк `skryabinsv/production-agentic-rag-course` на момент разбора совпадал с upstream, коммит `424a0eb`).
В нём: что курс даёт, где он слаб, какие риски несёт тем, кто перенесёт подход в прод, и что в этом форке исправлено.

## TL;DR

- **Сильная сторона курса — правильный порядок.** Сначала BM25, потом гибридный поиск. Пройден весь путь от ingestion до наблюдаемости, кэша, агента и канала доставки, и всё поднимается локально через Docker Compose.
- **Слабая сторона — слово «production» в названии.** В курсе нет оценки качества, нет аутентификации, все порты открыты наружу с дефолтными паролями. Цифры Recall/Precision на 3 статьях воспроизвести невозможно.
- **Код на `main` в значительной части не работал.** До правок тесты давали **76 passed / 4 failed / 35 errors**. Были сломаны парсинг PDF (Week 2), `/ask` и `/stream` (Week 5–6), трейсинг Langfuse (Week 6) и весь agentic-контур (Week 7). После правок: **177 passed, 0 failed**.
- **В форке закрыто большинство минусов и рисков.** Починены дефекты (§5), закрыты минусы и риски (§6): аутентификация и rate limit, пароли из `.env`, reranker, оценка каждого документа, память диалога, локальные эмбеддинги, неблокирующий ввод-вывод, оценка поиска и ответов. Что осталось открытым и почему — §7: выбор модели, security-плагин OpenSearch, несколько мелких пунктов.

## 1. Что за курс

7 недель, каждая неделя — это ноутбук, блог-пост и релизный тег:

| Неделя | Тема | Ключевые компоненты |
|---|---|---|
| 1 | Инфраструктура | Docker Compose: FastAPI, PostgreSQL 16, OpenSearch 2.19, Airflow 3, Ollama |
| 2 | Ingestion | arXiv API, Docling (парсинг PDF), Airflow DAG, PostgreSQL |
| 3 | Keyword search | OpenSearch BM25, Query DSL, фильтры |
| 4 | Chunking + hybrid | Секционный чанкинг, Jina v3 embeddings (1024d), нативный RRF в OpenSearch |
| 5 | RAG | Ollama (llama3.2:1b), промпт, SSE-стриминг, Gradio |
| 6 | Наблюдаемость и кэш | Langfuse v3 (self-hosted), Redis exact-match cache |
| 7 | Agentic RAG | LangGraph: guardrail → retrieve → grade → rewrite → generate, Telegram-бот |

## 2. Плюсы

1. **«Keyword first».** BM25 идёт до векторов, а гибрид собирается через RRF. Это честная и практичная позиция: многие туториалы прыгают сразу в vector DB.
2. **Сквозная система, а не набор сниппетов.** Есть данные (arXiv), пайплайн (Airflow), хранилища, поиск, генерация, наблюдаемость, кэш, агент и канал (Telegram). Видно, как всё стыкуется.
3. **Реалистичный парсинг.** Docling с выделением секций, ограничения по страницам и размеру, контролируемая конкурентность скачивания и парсинга.
4. **Нативный гибрид в OpenSearch** (search pipeline с `score-ranker-processor`/RRF) вместо ручного слияния в Python.
5. **Нормальная инженерная гигиена:** pydantic-settings, фабрики и DI через FastAPI, типизированные схемы, ruff и pre-commit, тесты. Graceful degradation hybrid → BM25 при сбое эмбеддингов.
6. **Наблюдаемость с первого дня продовой части:** Langfuse, user feedback по `trace_id`, метрики токенов и латентности.
7. **Агент собран явным графом:** узлы, условные переходы, ограничение числа попыток retrieval. Такой граф понятен и отлаживаем, в отличие от «магического» ReAct.
8. **Полностью локально и бесплатно** (кроме ключа Jina). MIT-лицензия, к каждой неделе есть подробный пост.

## 3. Минусы

Пометки в квадратных скобках показывают статус пункта в форке: подробности в §6, открытые пункты в §7.

### Методология
- **[закрыто]** **Нет оценки качества.** В README недели 4 есть таблица Recall@10/Precision@10, снятая на «3 papers, 81 chunks». Ни датасета, ни кода к ней нет. Без golden set нельзя понять, улучшил ли что-то новый чанкинг, `rank_constant` в RRF или рерайт запроса. Нет и оценки генерации: faithfulness, корректность цитат, отказ при отсутствии контекста.
- **[не решается кодом]** **Слишком слабая модель для агентных шагов.** `llama3.2:1b` должна выдавать структурированный JSON для guardrail и грейдинга. Для 1B это ненадёжно, а каждая неудача уходит в fallback. Ответ требует трёх последовательных вызовов LLM (guardrail, grade, generate), плюс rewrite.
- **[закрыто]** **«Document grading» — это одна бинарная оценка всего контекста целиком,** а не оценка каждого документа. Нерелевантные чанки не отфильтровываются.
- **[закрыто]** **Нет reranker'а** (cross-encoder) — стандартного шага между retrieval и генерацией в прод-RAG.
- **[закрыто для `/ask-agentic`]** **Нет диалоговой памяти.** `thread_id` формируется, но checkpointer не подключён, каждый запрос независим.

### Архитектура
- **[закрыто]** **Каждый чанк начинается с title + полного abstract.** Контекстный заголовок полезен, но целый абстракт в каждом чанке размывает эмбеддинги: все чанки статьи становятся похожи. При этом BM25 и так ищет по денормализованным полям `title`/`abstract`, так что абстракт засчитывается дважды.
- **[закрыто]** **Синхронные клиенты OpenSearch и Redis вызываются внутри async-эндпоинтов** и блокируют event loop. Отчасти это маскируется `--workers 4`.
- **[не менялось]** **`search_unified` глотает все исключения** и возвращает пустой результат. Упавший OpenSearch выглядит для пользователя как «ничего не найдено».
- **[закрыто: опция]** **Внешний платный API эмбеддингов (Jina)** конфликтует с тезисом про «complete data privacy». Тексты статей и вопросы уходят наружу. Зависимость `sentence-transformers` объявлена, но не используется.
- **[не менялось]** **Кэш не инвалидируется при появлении новых статей** (только TTL 6 ч). Ключ кэша — точное совпадение строки.
- **[частично]** **Удаление старых чанков и индексация новых не атомарны** (`replace_existing=True`). Если эмбеддинг упадёт посередине, статья пропадёт из поиска.
- Задача очистки в DAG чистит `/tmp/*.pdf`, а PDF кэшируются в `./data/arxiv_pdfs`, поэтому диск растёт бесконечно.

### Документация
- В README перечислены несуществующие эндпоинты (`/api/v1/papers`, `/api/v1/search`) и указан неверный порт Langfuse (3000 вместо 3001).
- Тесты не были защитной сеткой. Фикстуры для агентных тестов отсутствовали (35 ошибок на сборке). API-тесты патчили не те имена и на деле требовали живые сервисы, а часть ассертов принимала `500` как успех.

| Нет аутентификации и лимитов | `API_KEYS`, `RATE_LIMIT_PER_MINUTE=30` в `.env.example`. Gradio и скрипты оценки передают ключ из `API_KEY` | `src/security.py` |
| Дефолтные пароли захардкожены | Все пароли из `.env`. У Redis есть `requirepass`. Пароли MinIO и Langfuse-Redis больше не дублируются в двух местах. Пароль админа Airflow тоже из `.env` | `compose.yml`, `airflow/entrypoint.sh` |
| OpenSearch без аутентификации в клиенте | `OPENSEARCH__USERNAME/PASSWORD/USE_SSL/VERIFY_CERTS`. Сертификаты проверяются, если включён TLS | `opensearch/client.py` |
| Бот отвечает всем | Закрыт по умолчанию | `TELEGRAM__ALLOWED_USER_IDS`, `TELEGRAM__ALLOW_PUBLIC` |

## 7. Что не исправлено и почему

1. **Слабая модель.** Это выбор модели и железа, а не кода. `llama3.2:1b` по-прежнему стоит по умолчанию, потому что её скачивают ноутбуки курса. Для агентных шагов разумно `OLLAMA_MODEL=llama3.2:3b` или 8B. Влияние модели теперь можно измерить через `make eval-answers`. Структурированный вывод в Ollama ограничен JSON-схемой, так что формат ответа соблюдается; страдает качество самих суждений.
2. **Security-плагин OpenSearch в compose не включён.** Его включение требует TLS на 9200, пароля администратора, настройки Dashboards и правки всех ноутбуков (они ходят на `http://localhost:9200`). Кластер доступен только с `127.0.0.1`, а клиент уже умеет работать с защищённым кластером через `OPENSEARCH__*`.
3. **Память диалога в Telegram-боте.** Бот работает через простой RAG, а не через агента. Память и контекстуализация пока есть только в `/ask-agentic`.
4. **Явные ошибки поиска.** `search_unified` по-прежнему возвращает пустой результат при ошибке OpenSearch. Менять это нужно вместе с ноутбуками, которые на такое поведение рассчитывают.
5. **Инвалидация кэша при индексации** (версия индекса в ключе) и **полностью атомарная переиндексация.** Детерминированные `_id` уже исключают дубликаты, но шаг «удалить старое» в DAG выполняется до записи нового.
6. **Пины версий** (`langgraph`, `langchain`, `langfuse`, образ `minio/minio`) и **очистка PDF-кэша** в DAG.
7. **Реальная защита от prompt injection** невозможна в принципе. Разделители и инструкции снижают риск, но не устраняют его.

## 8. Миграция существующей установки

- **Индекс OpenSearch:** новые индексы создаются на движке `lucene`. Существующий `arxiv-papers-chunks` остаётся на `nmslib` и продолжает работать на 2.19, но не переживёт апгрейд на 3.x. Пересоздание: `OpenSearchClient.setup_indices(force=True)` и повторный прогон DAG `arxiv_paper_ingestion` (или ноутбука Week 4).
- **Порты:** сервисы теперь доступны только с `127.0.0.1`. Чтобы открыть API наружу, поменяйте `"127.0.0.1:8000:8000"` в `compose.yml` и поставьте перед ним аутентификацию.
- **`.env`:** добавьте новые переменные из `.env.example`: `OLLAMA_NUM_CTX`, `OLLAMA_TEMPERATURE`, `OLLAMA_ALLOWED_MODELS`, `TELEGRAM__ALLOWED_USER_IDS`, `LANGFUSE_INIT_USER_PASSWORD`. По умолчанию API принимает `OLLAMA_MODEL` и `llama3.2:3b` (обе используются в ноутбуках). Любую другую модель нужно добавить в `OLLAMA_ALLOWED_MODELS`, иначе API вернёт 422.
- **Кэш:** формат ключа изменился (нормализация запроса), старые записи просто истекут по TTL.
- **Чанки:** новый формат (абстракт отдельным чанком) применяется только при переиндексации. Старые чанки продолжают работать.
- **Пароли:** `REDIS__PASSWORD` в `.env.example` теперь задан, поэтому Redis стартует с паролем, а API берёт тот же пароль из `.env`. Хост-инструментам, например ноутбуку Week 6, нужен `export REDIS__PASSWORD=...`. `POSTGRES_PASSWORD` и `CLICKHOUSE_PASSWORD` применяются только при создании тома: для существующего тома оставьте старые значения или пересоздайте том.
- **API-ключи:** если задать `API_KEYS`, ноутбукам нужен заголовок `X-API-Key`, а Gradio и скрипты оценки берут ключ из переменной `API_KEY`.
- **Эмбеддинги:** смена `EMBEDDINGS__PROVIDER` требует пересоздать индекс. При расхождении API пишет предупреждение при старте.

## 9. Как проверить

```bash
uv sync
uv run pytest --ignore=tests/integration   # 177 passed (было: 76 passed, 4 failed, 35 errors)
make start
make eval GOLDEN=evals/my_set.jsonl                 # поиск
make eval-answers GOLDEN=evals/my_set.jsonl         # ответы
```

Изменения OpenSearch (движок `lucene`, гибридный запрос с фильтром в kNN-ветке, проверка search pipeline), запуск Redis с `requirepass` и загрузка локальных моделей (эмбеддинги, reranker) покрыты юнит-тестами и проверкой `docker compose config`, но не прогонялись на живом стеке. Перед использованием стоит один раз выполнить `make start`, ноутбук Week 4 и `make eval`.
